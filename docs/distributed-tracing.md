# Distributed tracing

This guide describes the backend tracing that is present in the repository. It
does not describe browser or mobile OpenTelemetry instrumentation.

## What is instrumented

- `initializeTracing()` starts the OpenTelemetry Node SDK during backend startup.
- Express middleware creates a server span for each request and records the
  method, URL, response status, and request identifiers.
- Correlation IDs are available in request/response headers:
  - `x-correlation-id` is accepted only when it contains safe characters and is
    no longer than 128 characters; otherwise the backend generates a UUID.
  - `x-request-id` is always generated by the backend for each request.
- `TracedHttpClient` creates client spans and forwards these headers when code
  uses that client. It does not automatically instrument every application
  Axios call.
- Node auto-instrumentation is enabled by the SDK configuration.

The backend records its trace service name as `OTEL_SERVICE_NAME`, defaulting to
`amana-protocol-backend`.

## Configuration

Set these variables in the backend environment. Example defaults are in
[`backend/.env.tracing.example`](../backend/.env.tracing.example).

| Variable | Purpose |
| --- | --- |
| `JAEGER_ENDPOINT` | HTTP endpoint for the Jaeger exporter |
| `ZIPKIN_ENDPOINT` | HTTP endpoint for the Zipkin exporter |
| `PROMETHEUS_PORT` | Port for the Prometheus metrics endpoint (`/metrics`) |
| `OTEL_SERVICE_NAME` | Service name attached to OpenTelemetry resources |
| `TRACE_BASELINE_RATE` | Probability from `0` to `1` for otherwise eligible spans; default `0.1` |
| `TRACE_ROUTE_OVERRIDES` | JSON map of URL substrings to sampling probabilities |

When both trace endpoints are configured, the current SDK setup passes only the
first configured exporter to the SDK (Jaeger is selected first). Configure one
trace exporter at a time. In production, the backend supplies a Jaeger endpoint
and Prometheus port when those values are unset.

## Sampling behavior and limitations

`TailBasedSampler` is a head sampler: it decides when a span starts, not after
the entire trace is available. It drops health, documentation, and metrics
routes, keeps configured high-value URL patterns, applies the longest matching
route override, and otherwise uses the baseline probability.

Despite the configuration name, this is not collector-side tail sampling.
Response status is normally known only after the sampling decision, and the
`TRACE_SLOW_THRESHOLD_MS` value is currently read but not used to make that
decision. To retain traces based on final status or duration, configure a
collector-side tail-sampling processor; that collector configuration is not
included in this repository.

The SDK can receive both Jaeger and Zipkin endpoint settings, but only one
exporter is wired into the current SDK instance. Exporter startup failures are
logged; the tracing initializer does not abort backend startup.

## Local verification

1. Start a Jaeger or Zipkin collector using its own documented local setup.
2. Set the corresponding endpoint and `PROMETHEUS_PORT` in the backend
   environment.
3. Start the backend with `npm run dev` from `backend/`.
4. Send a request and inspect the response's `x-correlation-id` and
   `x-request-id` headers.
5. Open the collector UI and inspect the backend service traces. If configured,
   query the metrics endpoint at `http://localhost:<PROMETHEUS_PORT>/metrics`.

The repository does not include a collector deployment or an end-to-end tracing
smoke test, so this guide does not claim that a collector export was exercised
as part of the project checks.
